# دستور اجرایی Agent — اتصال خودکار مدل‌ها به Laravel Calendar + انتخاب منابع هر تقویم

## نقش و مأموریت

تو توسعه‌دهنده ارشد Laravel/Livewire و مسئول تکمیل **همین مخزن موجود** `karnoweb/laravel-calendar` هستی. کد واقعی مخزن، PRD، برنامه پنج‌فازی قبلی و تصاویر مرجع UI را ابتدا بررسی کن. وظیفه تو تکمیل قابلیت‌های زیر در کد موجود است، نه ساخت یک پکیج دیگر یا بازنویسی بی‌دلیل هسته.

**هدف نهایی:** توسعه‌دهنده بتواند با قراردادن Trait `HasCalendarEvents` در مدل Eloquent (مدل پایگاه داده لاراول)، ثبت امن مدل به‌عنوان یک منبع و در صورت نیاز بازنویسی **یک متد** `calendarDefinition()`، نمایش، جست‌وجو، بارگذاری بازه‌ای، رنگ، فیلتر، مجوزها و عملیات تقویمی آن مدل را تنظیم کند. با وجود ثبت چندین مدل، هر **نمونه تقویم** بتواند فقط `tasks`، فقط `classes`، یا زیرمجموعه مشخص دیگری را نمایش دهد. هیچ قابلیت اصلی نسخه اول نباید ناتمام باقی بماند.

## اصول غیرقابل مذاکره

1. معماری فعلی مستقل از دیتابیس حفظ شود؛ Trait یک **آداپتور اختیاری** برای Eloquent است. `EventProvider` برای API، گوگل، تعطیلات و منابع غیردیتابیسی همچنان کار کند.
2. **Trait داشتن مساوی اجازه نمایش نیست.** اسکن خودکار همه مدل‌ها ممنوع؛ تنها مدل‌های ثبت‌شده در رجیستری سروری معتبرند. رجیستری یک‌بار هنگام راه‌اندازی برنامه ثبت شود؛ تأمین‌کننده داده تنها هنگام نیاز ساخته شود.
3. از ساخت Registry، Dispatcher، Engine یا سیستم مجوز موازی خودداری کن. موارد موجود مانند `CalendarBuilder`, `CalendarRegistry`, `SourceRegistry`, `ReadDispatcher`, `EmbedOptions`, `CalendarRuntime`, `EventProvider`, `ActionHandler` و DTOهای فعلی را بررسی و توسعه بده.
4. هیچ `App\\Models\\...`، جدول `tasks`، ماژول آموزش، شعبه، Mary UI یا ساختار کاربران میزبان را به هسته پکیج تحمیل نکن. هیچ migration اجباری اضافه نکن.
5. تمام محدودیت‌ها باید در سمت سرور اجرا شوند. پنهان کردن منبع در UI، امنیت یا محدودیت دسترسی محسوب نمی‌شود. بدون احراز هویت/مجوز خواندن، اطلاعات برنگردان؛ مگر برای تقویم عمومی که صریحاً و با مجوز سروری تعریف شده است.
6. تنظیمات و Handlerها در هر درخواست Livewire قابل بازسازی باشند. Closure (تابع بی‌نام) و مدل Eloquent یا Query Builder در State قابل سریال‌سازی Livewire ذخیره نشوند. از وابستگی وضعیت به درخواست قبلی جلوگیری کن.
7. نام‌ها و قراردادهای عمومی موجود را تا حد امکان حفظ کن؛ تغییر ناسازگار فقط پس از اثبات ضرورت، با تست و مستند مهاجرت مجاز است. برای قابلیت‌هایی که از قبل درست کار می‌کنند، کد تکراری نساز.
8. تست‌های قبلی باید سبز بمانند؛ نتیجه تست اجرا نشده را موفق اعلام نکن. هیچ فازی انتشار ناقص نیست؛ همه قابلیت‌های این دستور پیش از تأیید نهایی تکمیل شوند.

## بخش اول — قرارداد ساده مدل و Trait

### A. رابط اصلی توسعه‌دهنده

- Trait پیشنهادی: `HasCalendarEvents` در مسیر منطقی `src/Concerns/HasCalendarEvents.php` یا پوشه معادل هماهنگ با مخزن.
- متد قابل بازنویسی پیشنهادی: `calendarDefinition()`، بازگرداننده DTO تایپ‌شده `CalendarModelDefinition`.
- Trait باید **پیش‌فرض‌های معقول** برای نگاشت فیلدها، عنوان، رنگ، وضعیت، عنوان منبع، عملیات و فرم ارائه کند؛ تعریف حداقلی نباید به انبوهی از متدهای اجباری نیاز داشته باشد.
- `calendarDefinition()` بتواند یک‌جا این موارد را تعریف کند: کلید منبع، عنوان فارسی/انگلیسی، فیلدهای شروع/پایان، `allDay`، توضیح، وضعیت، دسته، رنگ/نشان، URL امن، شناسه/نسخه، قابلیت‌های مجاز، قوانین خواندن، نگاشت فیلترها، نگاشت عملیات نوشتن و فرم سفارشی.
- نگاشت مدل Task با `scheduled_for` و پایان محاسبه‌ای پیش‌فرض (مثلاً یک ساعت بعد) بدون تغییر Schema موجود کار کند؛ مدل Class با `starts_at`/`ends_at` و بازه‌های چندروزه هم کار کند. نام ستون مشخص و یکسان برای همه مدل‌ها اجباری نیست.
- تعریف باید در سطح **نوع مدل** قابل دریافت باشد و برای ساخت کوئری لازم نباشد تمام رکوردها را بارگذاری کنیم. اگر مقدار رنگ/عنوان/مجوز به یک رکورد وابسته است، ارزیابی آن فقط برای رکوردهای صفحه جاری انجام شود.
- اگر برای یک ماژول پیچیده قرارداد توصیفی کافی نبود، امکان معرفی Handler/Provider سفارشی در همان تعریف وجود داشته باشد؛ مسیر ساده را پیچیده نکن.

### B. ثبت امن مدل

- یک روش واحد و مستند برای ثبت منبع مدل معرفی کن؛ مثلاً رجیستری مدل‌ها در Service Provider میزبان با نام‌های پایدار `tasks`, `classes`, `meetings`.
- رجیستری باید تکرار کلید، کلاس نامعتبر، مدل فاقد Trait یا تعریف ناقص را با خطای روشن رد کند.
- هیچ جست‌وجوی خودکار در کل پوشه `app/Models`، فراخوانی همه مدل‌ها یا کار زمان‌بر هنگام هر درخواست انجام نده.
- رجیستری خودکار یک `EloquentEventProvider` متناسب با هر مدل ثبت‌شده بسازد یا با آداپتور امن به `EventProvider` فعلی متصل شود. نام/ثبت تأمین‌کننده برای تمام مراحل خواندن و عملیات یکسان باشد.
- پشتیبانی Providerهای قبلی و Google/Holidays را حفظ کن. رجیستری مدل با کلیدهای دستی Provider تداخل نداشته باشد.

## بخش دوم — مسئله اصلی: انتخاب منابع برای **هر تقویم**

### سه لایه کاملاً جدا

**لایه ۱ — منابع ثبت‌شده:** مدل‌هایی که میزبان به‌صورت امن معرفی کرده (`tasks`, `classes`, `meetings`, ...). ثبت به‌معنی لود همیشگی یا مجوز خواندن نیست.

**لایه ۲ — منابع مجاز یک تقویم:** `CalendarDefinition`/Factory در سرور مشخص می‌کند که مثلاً تقویم شخصی فقط `tasks` داشته باشد، تقویم آموزشی فقط `classes` و تقویم جامع `tasks+classes+meetings`.

**لایه ۳ — منابع فعالِ نمایش:** داخل همان مجموعه مجاز، کاربر می‌تواند فیلترها را روشن/خاموش کند. این فیلتر فقط محدودکننده است و هرگز منبع جدید به مجموعه مجاز اضافه نمی‌کند.

### رفتارهای الزام‌آور

1. اگر سه مدل Trait دارند و ثبت شده‌اند، تقویم جامع می‌تواند هر سه را نشان دهد.
2. یک کامپوننت دیگر با `sources=['classes']` **فقط** کلاس‌ها را می‌خواند و فقط قوانین کلاس را اجرا می‌کند؛ حتی متد `fetch` برای Tasks فراخوانی نشود.
3. یک کامپوننت دیگر با `sources=['tasks']` فقط تسک‌ها را نمایش می‌دهد، حتی وقتی روی همان صفحه تقویم جامع هم وجود دارد.
4. انتخاب منابع در تعریف تقویم و/یا پارامتر سروری کامپوننت باید از قابلیت موجود `CalendarBuilder::sources()` و `EmbedOptions::sources` استفاده کند. اگر یک API خوش‌خوان جدید پیشنهاد می‌دهی، آن را به همین قرارداد متصل کن نه اینکه موتور انتخاب مستقل ایجاد کنی.
5. مقدار `null` برای فهرست منابع: مطابق رفتار مستند موجود، تمام **منابع مجاز همان CalendarDefinition**؛ نه تمام مدل‌های موجود برنامه. آرایه خالی `[]` هرگز به معنی «نمایش همه» نشود: یا از ابتدا رد شود یا به حالت امنِ بدون منبع ختم شود؛ تصمیم را یکسان در API، تست و مستند تثبیت کن.
6. کلید ناشناخته، کلید تکراری و منبع غیرمجاز از سمت مرورگر/URL/Livewire هیچ‌وقت به رجیستری Provider تبدیل نشوند. برای تنظیم اشتباه میزبان خطای قابل فهم بده و برای درخواست جعلی به شکل امن رد کن.
7. محدودسازی منابع باید روی **همه مسیرها** یکسان اعمال شود: بارگذاری شبکه، جست‌وجو، شمارش، مودال روز، جزئیات رویداد، ساخت، ویرایش، حذف، انتقال، Resize (تغییر مدت)، تکرار، فیلترها، «بیشتر»، بازخوانی و هر API فعلی.
8. فرم ساخت رویداد تنها منابع مجاز و قابل ساخت همان تقویم را نشان دهد. اگر فقط یک منبع قابل ساخت است، انتخاب منبع را خودکار انجام بده و فیلد انتخاب را مخفی کن.
9. فیلترهای منابع ناموجود در همان تقویم نمایش داده نشوند. اگر فقط یک منبع وجود دارد، بخش فیلتر منبع به‌صورت خودکار مخفی/ساده شود.
10. دو تقویم هم‌زمان در یک صفحه، با فیلترها و وضعیت‌های مستقل، نباید داده، وضعیت URL، کش یا عملیات یکدیگر را تغییر دهند؛ از `instanceId`/`urlPrefix` موجود استفاده کن.
11. انتخاب یک تقویم محدودشده به کلاس‌ها با دستکاری شناسه رویداد Tasks در درخواست نوشتن باید قاطعانه رد شود، حتی اگر همان کاربر در تقویم جامع حق تغییر Tasks داشته باشد.
12. میزبانی که یک ماژول را خاموش کرده، بتواند آن منبع را در تعریف همان تقویم حذف کند. تغییر تعریف در درخواست بعدی باید فوری و امن اعمال شود.

### سناریوهای کاربردی الزامی برای مستندات

- «تقویم من»: فقط تسک‌های مجاز کاربر.
- «تقویم آموزشی»: فقط کلاس‌های مجاز مجموعه؛ بدون بارگذاری Tasks.
- «تقویم جامع»: Tasks + Classes + Meetings، با فیلتر منابع.
- «ویجت کلاس‌ها» کنار «ویجت تسک‌ها» روی یک داشبورد و بدون تداخل.
- «تقویم مدیر»: منابع و رکوردهایی که نقش مدیر اجازه مشاهده دارد، نه دسترسی پیش‌فرض به تمام داده‌ها.

## بخش سوم — دریافت خودکار داده فقط در **بازه قابل مشاهده**

1. بازه قابل مشاهده را با همان `CalendarEngine` و `DateRange` موجود محاسبه کن؛ در نمای ماه، روزهای تکمیل‌کننده هفته‌های ابتدایی/انتهایی نیز بخشی از بازه هستند. هفته/روز/لیست بازه متناسب خود را داشته باشند.
2. تقویم شمسی صرفاً شیوه نمایش/ناوبری است؛ بازه محاسبه‌شده را برای کوئری به تاریخ و زمان استاندارد میلادی و منطقه زمانی معتبر تبدیل کن. از فیلترکردن پس از دریافت رکوردهای کل جدول پرهیز کن.
3. **قاعده هم‌پوشانی بازه:** زمان شروع رویداد پیش از انتهای بازه و زمان پایان رویداد پس از ابتدای بازه باشد. بازه‌ها `[start,end)` هستند (انتهای بازه شامل نمی‌شود). رویداد شروع‌شده در ماه قبل و ادامه‌دار در ماه جاری باید دیده شود.
4. برای رویدادهای زمان‌دار و تمام‌روز، تبدیل Timezone (منطقه زمانی)، DST (تغییر ساعت تابستانی)، پایان غیرشامل، تاریخ پایان محاسبه‌ای و `null`-بودن انتها را دقیق و با تست مدیریت کن.
5. نگاشت استاندارد فیلدها تا حد ممکن با Eloquent Query Builder انجام شود؛ `where` تاریخ، `where` وضعیت، `where` مالکیت/دامنه، جست‌وجو و مرتب‌سازی را قبل از اجرای کوئری اضافه کن. تبدیل هر رکورد به `CalendarEventData` بعد از اعمال `limit`/pagination (صفحه‌بندی) انجام شود.
6. کنترل دامنه داده باید **در خود کوئری دیتابیس** اعمال شود، نه بعد از گرفتن داده‌ها. برای مدل‌های خصوصی اگر قاعده خواندن سروری تعریف نشده است، دسترسی را به‌صورت پیش‌فرض رد کن. یک مدل فقط با داشتن `user_id` به‌طور خودکار برای همه کاربران آزاد نشود.
7. صفحه‌بندی موجود `EventPage`, `EventQuery`, `ReadDispatcher` و cursor را حفظ کن. فقط منابع انتخاب‌شده را کوئری بزن؛ از دریافت بی‌حد و پردازش همه رکوردها در حافظه پرهیز کن. `with` لازم برای روابط نمایشی را به‌صورت اختیاری و کنترل‌شده پشتیبانی کن تا N+1 (کوئری تکراری) رخ ندهد.
8. جست‌وجو و فیلترهای status/category/source تا جای ممکن در SQL انجام شوند. برای فیلترهای محاسباتی یا روابط خاص، رفتار بهینه یا Handler سفارشی قابل تعریف باشد.
9. برای رویدادهای تکراری، occurrence (وقوع) فقط داخل بازه مورد نیاز و زیر سقف قابل تنظیم تولید شود؛ فهرست نامحدود تکرارها تولید نشود.
10. کش اختیاری اگر فعال است، باید calendar key، منابع انتخاب‌شده، دامنه، کاربر، فیلتر، تاریخ و نسخه داده را در کلید لحاظ کند؛ پس از تغییر موفق، اطلاعات مرتبط باطل شود. کش بین دو tenant/user یا دو تقویم مختلف نشت نکند.
11. برای کوئری‌های پرتکرار، ایندکس‌های پیشنهادی مانند ستون‌های دامنه+شروع/پایان را در مستند میزبان پیشنهاد کن؛ migration اجباری در پکیج ایجاد نکن.

## بخش چهارم — قوانین و عملیات مدل‌محور

- از `calendarDefinition()` قوانین پیش‌فرض نمایش، رنگ، فیلتر و قابلیت‌ها استخراج شوند. پیاده‌سازی ساده صرفاً با Trait و همین متد قابل استفاده باشد.
- به‌صورت اختیاری قابلیت‌های create/edit/delete/move/resize/status/customAction/recurrence قابل تنظیم باشند. امکان Handler سفارشی برای عملیات پیچیده فراهم بماند.
- در هر درخواست نوشتن: CalendarDefinition تازه از سرور resolve شود؛ مجازبودن source بررسی شود؛ رکورد داخل دامنه کاربر دوباره query/find شود؛ مجوز عمل همان لحظه بررسی شود؛ `expectedVersion` و `operationId` در صورت نیاز بررسی شوند؛ عملیات در Transaction (تراکنش دیتابیس) امن انجام شود؛ رویداد پس از موفقیت ارسال شود؛ سپس کش مرتبط باطل گردد.
- readonly (فقط‌خواندنی) بودن منبع، منو، قابلیت‌های کارت و متدهای Livewire را یک‌جا محدود کند، نه فقط دکمه‌ها را.
- Drag & Drop و Resize باید مدت رویداد و ساعت درست را حفظ کنند و با قطع ارتباط، خطای اعتبارسنجی یا تعارض، UI به وضعیت معتبر بازگردد.
- رویدادهای چندروزه در ماه به‌صورت نوار ادامه‌دار، در هفته در ناحیه all-day/multi-day، در روز همراه با نشانه ادامه و در لیست همراه با بازه کامل نمایش داده شوند.
- عملیات تکرار شامل همین وقوع، وقوع‌های آینده و کل مجموعه، با استثناها و اعتبارسنجی سمت سرور باشد.
- فرم سفارشی مدل و فرم پیش‌فرض عمومی هر دو قابل استفاده باشند؛ داده فرم فقط برای فیلدهای مجاز هر منبع پذیرفته شود.
- تکمیل خودکار فیلترهای status/category، عنوان منبع، رنگ، عملیات سفارشی و لینک جزئیات از تنظیمات مدل، با قابلیت Override (جایگزینی) سروری انجام شود.

## بخش پنجم — سه کامپوننت و تجربه کاربری

- `FullCalendar`: ماه/هفته/روز/لیست، شمسی/میلادی، فیلتر و جست‌وجو، عملیات کامل، رویدادهای چندروزه، صفحه‌بندی و مدیریت خطا.
- `MiniMonth`: تقویم فشرده با نقطه/شمارنده رویدادها، امروز، روز انتخابی و نمایش کم‌حجم رویدادهای چندروزه. باید بتواند فقط `classes` یا `tasks` دریافت کند.
- `UpcomingAgenda`: رویدادهای آینده یا روز انتخابی با تعداد قابل تنظیم و empty state (حالت خالی) مناسب. در حالت فقط `classes` نباید حتی یک تسک از سرور بارگذاری شود.
- به‌جای سه موتور خواندن متفاوت، سه نمای متفاوت روی یک هسته Provider، Definition، Range و مجوز بساز. از کد موجود `layout='compact'` در صورت کفایت استفاده کن و آن را بدون دلیل نشکن.
- تصاویر مرجع UI همراه درخواست را راهنمای کیفیت بصری قرار بده؛ light/dark و RTL/LTR، صفحه موبایل/تبلت/دسکتاپ، کنتراست، خوانایی کارت‌ها، تمیزبودن toolbar و sidebar را رعایت کن. متن دمو و رنگ/فاصله را به شکل غیرقابل تنظیم hardcode نکن.
- وضعیت فیلتر داخل نمونه تقویم باید روشن باشد: «فقط کلاس» یک محدودیت ثابت سرور است، نه تیک اختیاری که کاربر بتواند Tasks را روشن کند.

## ترتیب پیاده‌سازی — پنج گام اجرایی، بدون انتشار ناقص

**گام ۱ — ممیزی و تثبیت قراردادها:** تمام مسیرهای فعلی مربوط به Provider، Builder، EmbedOptions، SourceRegistry، ReadDispatcher، اعمال عملیات، ویجت‌ها و تست‌ها را مشخص کن؛ فهرست قابلیت موجود/ناقص را در `docs/CALENDAR-MODEL-INTEGRATION-STATUS.md` بنویس. قرارداد `CalendarModelDefinition` و نحوه ثبت مدل را تصویب و مستند کن.

**گام ۲ — Trait و آداپتور Eloquent:** Trait، تعریف مدل، رجیستری سروری، آداپتور Provider، نگاشت رکورد، Scope خواندن و اتصال مجوزها/عملیات را بساز. با Task و Class واقعی در Workbench (محیط نمونه پکیج) اثبات کن.

**گام ۳ — محدودیت منابع + کوئری بازه‌ای:** مسیرهای `CalendarBuilder`, `EmbedOptions`, `ReadDispatcher`, `SourceRegistry`, `ReadRequest`, فیلترها و تمام عملیات را یکسان کن. اشکال `sources=[]` را اصلاح کن؛ از کوئری ناخواسته روی منابع حذف‌شده جلوگیری کن. تست SQL/Query Count، هم‌پوشانی چندروزه و شمسی را اجرا کن.

**گام ۴ — UI و امکانات محصول:** سه کامپوننت، رویداد چندروزه، فرم‌های مدل، انتخاب خودکار منبع یکتا، فیلتر هوشمند، تغییر مدت، اکشن‌های سفارشی، جست‌وجو، حالت‌های خالی و responsive را با تصاویر مرجع و هسته فعلی هماهنگ کن.

**گام ۵ — امنیت، یکپارچگی، تست و مستندات:** مسیر تقویم شخصی فعلی را با آداپتور بدون migration اجباری پوشش بده، مثال‌های مصرف‌کننده ایجاد کن، همه تست‌ها را اجرا و خروجی قابل بازبینی ارائه کن. تا پایان همه موارد، اعلام Production-ready ممنوع است.

## تست‌های پذیرش اجباری

برای هر مورد تست واحد/ویژگی و در موارد ظاهری تست مرورگر با داده واقعی بساز:

1. مدل Task و Class هر دو Trait دارند؛ رجیستری هر دو را شناخته و منبع یکتا می‌سازد.
2. تقویم جامع هر دو منبع را نمایش می‌دهد.
3. تقویم `sources=['classes']` فقط کلاس‌ها را برمی‌گرداند؛ تعداد فراخوانی Provider تسک **صفر** است.
4. تقویم `sources=['tasks']` فقط تسک‌ها را برمی‌گرداند؛ تعداد فراخوانی Provider کلاس **صفر** است.
5. دو تقویم محدودشده در یک صفحه مستقل کار می‌کنند.
6. فعال‌کردن فیلتر Tasks با URL یا Livewire در تقویم کلاس‌ها هیچ داده‌ای از Tasks نشان نمی‌دهد.
7. ارسال شناسه رویداد Task به عملیات edit/delete/move/resize در تقویم فقط کلاس با رد دسترسی مواجه می‌شود و دیتابیس تغییری نمی‌کند.
8. آرایه خالی `sources=[]` هرگز تمام منابع را فعال نمی‌کند.
9. منبع ناشناخته/تکراری/ثبت‌نشده رد می‌شود.
10. غیرفعال‌شدن ماژول آموزش در Factory سروری، نمایش و عملیات کلاس‌ها را متوقف می‌کند.
11. بازکردن نمای ماه شمسی فقط بازه واقعی شبکه را از دیتابیس می‌خواند.
12. رویدادی که از ماه قبل شروع شده و در ماه جاری ادامه دارد دیده می‌شود؛ رویداد خارج از بازه دیده نمی‌شود.
13. رویداد با پایان دقیقاً برابر شروع بازه جدید به اشتباه در آن بازه نشان داده نمی‌شود.
14. مدل `scheduled_for` بدون `ends_at` از پایان محاسبه‌ای درست استفاده می‌کند.
15. عبور از نیمه‌شب، سال نو شمسی، DST و رویداد تمام‌روز با پایان غیرشامل صحیح است.
16. در جدول با ده‌ها هزار رکورد، حجم داده خوانده‌شده و تعداد کوئری وابسته به بازه/limit است نه اندازه کل جدول.
17. محدودیت user/tenant در سطح SQL اعمال می‌شود؛ کاربر A رکورد کاربر B را در خواندن، جست‌وجو، جزئیات یا نوشتن نمی‌بیند.
18. عدم تعریف Scope خواندن برای مدل خصوصی، داده‌ای لو نمی‌دهد.
19. N+1 در تبدیل رکوردهای دارای رابطه رخ نمی‌دهد.
20. pagination، `hasMore` و ترکیب چند منبع بدون تکرار/حذف اشتباه کار می‌کنند.
21. فیلترهای source/status/category فقط روی مجموعه مجاز همان تقویم عمل می‌کنند.
22. اگر فقط یک منبع قابل ساخت است، فرم آن را پیش‌انتخاب می‌کند؛ عملیات ساخت همچنان سروری اعتبارسنجی می‌شود.
23. منبع readonly هیچ عملیات نوشتنی را حتی با درخواست مستقیم قبول نمی‌کند.
24. عملیات Move/Resize موفق، ناموفق، تکراری، stale و لغوشده وضعیت صحیح UI و دیتابیس دارند.
25. تغییرات رویداد تکراری در دامنه این وقوع/آینده/همه درست اعمال می‌شوند.
26. رویداد چندروزه در چهار نمای تقویم، MiniMonth و Agenda به‌درستی دیده می‌شود.
27. حالت‌های light/dark، RTL/LTR، موبایل، دسکتاپ، لمس و صفحه‌کلید بدون خطای کنسول تست شوند.
28. cache در کلید actor+scope+calendar+selectedSources+range+filters ایزوله است؛ تغییر داده کش مناسب را باطل می‌کند.
29. تغییر calendar definition در درخواست جدید بر اساس منبع‌های سروری دوباره اعمال می‌شود، حتی اگر state قبلی Livewire باقی مانده باشد.
30. تمامی تست‌های قبلی پروژه همچنان سبز هستند و هیچ قرارداد عمومی بدون مستند مهاجرت شکسته نشده است.

## مستندات اجباریِ تحویل

- `docs/MODEL-TRAIT-INTEGRATION.md`: صفر تا صد افزودن Trait، یک متد تعریف، رجیستری مدل‌ها، نگاشت ستون‌های متفاوت، فرم، مجوز و فیلتر.
- `docs/CALENDAR-SOURCE-SELECTION.md`: سه لایه منابع، مثال «همه / فقط Tasks / فقط Classes / ترکیبی»، استفاده در Full/Mini/Agenda، امنیت و رفتار `null` در مقابل `[]`.
- `docs/QUERY-PERFORMANCE.md`: تعیین بازه مرئی، کوئری هم‌پوشانی، زمان/شمسی، صفحه‌بندی، ایندکس پیشنهادی، محدودیت‌های کش، تست بار.
- `docs/CALENDAR-MODEL-INTEGRATION-STATUS.md`: گزارش مرحله‌ای، فایل‌های تغییرکرده، تصمیم‌ها، کارهای ناقص، تست‌های واقعی و ریسک‌ها.
- مثال Workbench با Task، EducationalClass، Meeting، یک تقویم جامع و دو تقویم محدودشده در یک داشبورد.
- راهنمای ارتقا و سازگاری برای استفاده‌کنندگان قبلی از `EventProvider` و `CalendarBuilder::sources()`.

## قالب گزارش Agent بعد از هر گام

1. چه کدی واقعاً تغییر کرده و چرا (فایل و مسیر دقیق).
2. چه امکاناتی تکمیل شده و چه مواردی هنوز ناقص‌اند.
3. نام تست‌ها، دستور واقعی اجرا و خروجی واقعی؛ اگر محیط وابستگی ندارد، صریحاً «اجرا نشد» بنویس.
4. ریسک‌های امنیتی و کارایی باقی‌مانده.
5. تصمیم‌های معماری جدید و علت آن‌ها.
6. اعلام قبولی گام فقط پس از قبولی معیارهای همان گام؛ اعلام آمادگی انتشار فقط پس از پایان تمام گام‌ها و مرورگر.
